## D-0001 — Технологический стек MVP

**Дата:** 12 августа 2026 (пересмотрено после полного документального аудита)
**Статус:** Принято (YELLOW — техническое, обратимое, не product-decision)

**Процесс.** Первая версия этого решения (та же дата, более раннее время) была принята без систематической проверки — по принципу «стандартная технология». Это было явно указано как недопустимое: *«STANDARD TECHNOLOGY ≠ AUTOMATICALLY CORRECT TECHNOLOGY»*. Решение переделано по чек-листу из 10 пунктов, с фактическим построчным чтением всех 45 архитектурных документов, а не по памяти.

**1. Прочитана вся релевантная документация.** Все документы `/docs` (45 файлов, включая парные/похожие) прочитаны целиком, не выборочно. Список — в разделе «Аудит документации» ниже. *Исправление (13 августа 2026, по итогам внешнего архитектурного review):* ранее здесь и в паре других мест ошибочно указывалось 46 — `First.md` (пустой файл, см. «Находка 5» ниже) изначально существовал только в Project Knowledge, не в самом репозитории `/docs`, и был удалён ещё до начала работы над проектом — он никогда не входил в реальный docs-аудит, счёт в 46 включал его по ошибке.

**2. Реальные требования системы (извлечены из документов, не предположены):**
- Модульные слои DATA → ANALYSIS → KNOWLEDGE → DECISION → AI → UI → LEARNING, каждый заменяемый (`23_SYSTEM_ARCHITECTURE.md`, `17_SYSTEM_ARCHITECTURE_MAP.md`)
- AI provider обязан быть абстрагирован через `AI_SERVICE → AI_PROVIDER_ADAPTER`, с поддержкой vision-моделей для анализа визуального контента (`29_AI_LAYER.md` §2-9, `04_ANALYTICAL_ENGINE.md` §8-9 — карусели и Reels требуют визуального анализа)
- Структурированный AI-output с валидацией, версионированием prompt/model (`29_AI_LAYER.md` §11, §22-23)
- Асинхронная обработка через job queue для sync/анализа/AI (`24_TECHNICAL_ARCHITECTURE.md` §21-22, `31_INFRASTRUCTURE_DEPLOYMENT.md` §11-15)
- Реляционная БД с версионированными миграциями, множественными связанными сущностями (`25_DATABASE_SCHEMA.md` §67, `18_DATA_MODEL.md`, `22_DATA_MODEL.md`)
- Object storage отдельно от реляционной БД для медиа (`31_INFRASTRUCTURE_DEPLOYMENT.md` §17, `38_COST_SCALABILITY_MODEL.md` §17)
- REST API с версионированием, OpenAPI-совместимой документацией, async job pattern (`27_API_CONTRACTS.md`, весь документ — 72 пункта, детальный контракт уже специфицирован)
- Observability: структурированные логи, метрики, error tracking, AI cost/latency tracking (`36_OBSERVABILITY_MONITORING.md` §72 MVP-минимум)
- Push/email/in-app notifications (`34_NOTIFICATIONS.md`)

**3. Ограничения integrations.** Основная интеграция — Instagram (`08_METRICS_FRAMEWORK.md`). Instagram Graph API требует: OAuth2, business/creator аккаунт на стороне пользователя, rate limits, не всегда webhook-поддержка → нужен polling + incremental sync (`26_DATA_PIPELINE.md`, `38_COST_SCALABILITY_MODEL.md` §25-26).

**4. Data model.** Сильно реляционная модель (User→Goal→Content→ContentFeature→Performance→Pattern→Recommendation→Decision→Outcome, множественные FK, история изменений) — не документная и не graph-модель. Реляционная БД подходит напрямую (`18_DATA_MODEL.md`, `25_DATABASE_SCHEMA.md`).

**5. Authentication.** Нужен свой account-слой + OAuth-поток для внешней платформы (`27_API_CONTRACTS.md` §5, `30_SECURITY_PRIVACY.md` §69).

**6. AI provider abstraction.** Проверено на соответствие `29_AI_LAYER.md`: провайдер должен поддерживать text + vision, structured output, capability registry. Anthropic Claude API удовлетворяет этим требованиям на сегодня; выбор провайдера отделён от бизнес-логики интерфейсом `AIProvider`, так что смена провайдера в будущем не требует переписывания Recommendation Engine — это прямое архитектурное требование, не предпочтение.

**7. Deployment requirements.** MVP-инфраструктура по `31_INFRASTRUCTURE_DEPLOYMENT.md` §10-11: frontend → backend API → database + отдельный background worker. Cloud provider архитектурно не обязателен (§61) — выбор конкретного хостинга это отдельное решение внутри уже выбранного стека, не блокирующее сам стек.

**8. Testing requirements.** Нужны unit/integration/API/E2E тесты, contract tests между frontend и backend, AI evaluation harness (`35_TESTING_QUALITY_CONTROL.md`, `27_API_CONTRACTS.md` §49).

**9. Рассмотренные альтернативы:**
- **Next.js (TS) монорепо + PostgreSQL + Prisma** — выбрано
- **NestJS backend + отдельный React/Vite frontend** — даёт более строгое DI-разделение слоёв «из коробки», но для соло-разработки означает два деплоя, два CI-пайплайна, больше инфраструктурной поверхности без явной пользы на MVP-стадии
- **Python (FastAPI) backend** — сильнее для будущих ML/data-science задач (если Content Analysis Engine когда-то потребует собственные модели, а не только вызовы AI provider), но два языка в соло-проекте увеличивают нагрузку на поддержку; сегодня вся «интеллектуальная» работа идёт через внешний AI provider API, а не через собственные ML-модели, поэтому преимущество Python не реализуется на MVP-стадии

**10. Оценка последствий:** Next.js/TS выбор принят. Главное следствие — логическое разделение слоёв (Data/Analysis/Knowledge/Decision/AI/UI) не обеспечивается физической границей процессов, а держится только дисциплиной структуры папок и code review. Это явно разрешено `23_SYSTEM_ARCHITECTURE.md` §72 (MVP_ARCHITECTURE), но это осознанный компромисс, а не бесплатный выбор — если дисциплина нарушится, слои начнут смешиваться незаметно (см. §13 ARCHITECTURAL DRIFT в операционных правилах). Зафиксировано в `CLAUDE.md` как обязательное правило структуры.

**Итоговый стек:**
- Язык: TypeScript везде
- Frontend + Backend: Next.js (App Router), монорепо
- БД: PostgreSQL, ORM/миграции: Prisma
- Очередь/воркеры: BullMQ + Redis
- Аутентификация: Auth.js (+ OAuth для Instagram)
- Object storage: S3-совместимое (Cloudflare R2) через `ObjectStorageService`-абстракцию — не прямые вызовы provider SDK по коду (`31_INFRASTRUCTURE_DEPLOYMENT.md` §62)
- AI provider: Anthropic Claude API через `AIProvider`-интерфейс (text + vision), с capability registry на будущее для мультипровайдера
- Observability: Sentry (errors), структурированные логи (pino) + Vercel logs, AI usage/cost tracking — свой слой поверх AI_SERVICE
- Хостинг MVP: Vercel (app) + managed Postgres (Neon) + managed Redis (Upstash) + R2 — все за абстракциями, замена провайдера не должна требовать переписывания domain logic
- CI: GitHub Actions
- Тесты: Vitest (unit/integration), Playwright (E2E), contract tests для критичных endpoints

**Последствия:** см. пункт 10. Стек пересматривается при появлении evidence против него (узкое место AI-пайплайна, рост стоимости managed-сервисов и т.д.), а не по личному предпочтению.

## D-0002 — Результаты документального аудита и иерархия документов

**Дата:** 12 августа 2026
**Статус:** Принято (YELLOW — документационная гигиена, не меняет продуктовый смысл)

**Контекст.** В репозитории обнаружены две волны документации: ранняя (файлы `04`–`16`, частично на английском, более концептуальные) и поздняя (файлы `17`–`46`, на русском, значительно детальнее и архитектурно строже). Часть ранних документов тематически дублируется поздними. Проверка на противоречия была явно запрошена перед стартом реализации.

**Находка 1 — реальный дубль.** `06_RECOMMENDATION_ENGINE.md` (8K, ранняя версия) и `13_RECOMMENDATION_ENGINE.md` (32K, поздняя версия) описывают один и тот же компонент. `13` полностью покрывает и расширяет `06`, за одним исключением: `06` содержит конкретную структуру ежедневного вывода (Daily Overview, секции A–F), которая не встречается дословно в `13`, но семантически покрыта `20_USER_JOURNEY.md` и `33_UX_USER_FLOWS.md`.
**Решение:** `13` считается авторитетным источником по Recommendation Engine. `06` помечается как historical/superseded (не удаляется — файлы не удаляются без разрешения Olga), на него не следует ссылаться в новых задачах.

**Находка 2 — сужение категорий, не противоречие.** Ранние документы (`05_GOAL_FRAMEWORK.md`, `08_METRICS_FRAMEWORK.md`, `09_PATTERN_DETECTION.md`, `10_STRATEGY_LIBRARY.md`) включают комментарии и репосты как равноправные цели/метрики. Поздние документы (`13`, `16_CONTENT_ANALYSIS_ENGINE.md` §12, `19_MVP_SCOPE.md` §17, `21_DECISION_LOGIC.md` §8) последовательно и единогласно исключают комментарии и репосты из основного recommendation layer, оставляя 4 категории: likes/followers/saves/reach.
**Решение:** это не конфликт, а осознанное сужение scope в поздней архитектуре. Комментарии и репосты **собираются** как данные (`08_METRICS_FRAMEWORK.md` остаётся в силе для data collection), но **не участвуют** в primary recommendation categories. Зафиксировано явно, чтобы это не пришлось угадывать заново в середине реализации.

**Находка 3 — существенное пересечение без противоречий (кандидаты на будущую консолидацию, не блокирует Phase 0):**
- `35_TESTING_QUALITY_CONTROL.md` и `43_TESTING_AND_QUALITY_ASSURANCE.md` — оба про тестирование, пересекаются в CI/test environments/quality gates, но каждый содержит и уникальный материал (35: AI evaluation, data quality score, race conditions; 43: bug severity, release blockers, model/prompt/schema change process)
- `31_INFRASTRUCTURE_DEPLOYMENT.md` и `37_DEPLOYMENT_RELEASE_STRATEGY.md` — 31 про инфраструктурные компоненты, 37 про процесс релиза; пересекаются в environments/rollback, но не противоречат
- `19_MVP_SCOPE.md` и `41_MVP_SCOPE_AND_PRIORITIES.md` — на первый взгляд дубли по названию, на деле разные: 19 = что входит в MVP функционально, 41 = процесс принятия решений о приоритетах. Дублирования нет.
- `20_USER_JOURNEY.md` и `33_UX_USER_FLOWS.md` — заметное пересечение в описании recommendation flow и outcome-статусов
**Решение:** ни одна из этих пар не блокирует старт реализации — противоречий не найдено, только избыточность изложения. Рекомендуется объединить каждую пару в один документ на более позднем этапе (не Phase 0), если это не потребует решений, которые входят в компетенцию Olga.

**Находка 4 — технический артефакт, не проблема репозитория.** Пять `.pdf`-файлов (`Brand_Voice__Personal_Profile.pdf`, `Swipe_File.pdf`, `The_Word.pdf`, `Полное_руководство.pdf`, `Полное_hуководство_дополнительно.pdf`) при попытке прочитать их как обычный PDF оказались ZIP-архивами с постраничными jpeg + txt + manifest.json. Это стандартный способ, которым среда предпросмотра индексирует PDF для поиска, а не повреждение файлов в репозитории Olga. Содержательно эти файлы — материалы личного бренд-войса и swipe-file для контента (не архитектурная документация), релевантны скорее для onboarding AI Assistant (`11_AI_ASISISTANT.md` §12, Option A: Upload Existing Materials), чем для Phase 0.

**Находка 5 — пустой файл.** `First.md` — 0 байт. Не блокирует Phase 0, но стоит либо удалить (требует разрешения Olga — деструктивная операция), либо наполнить содержанием, если он задумывался как точка входа.

**Итог аудита:** ни одно найденное расхождение не поднимается до уровня RED (не влияет на продуктовый смысл, не создаёт architecture conflict, не требует решения Olga). Все обработаны как YELLOW и задокументированы здесь. Полный список дубли-кандидатов сохранён для консолидации после MVP, не до него.

1. App Authentication и Instagram Integration — разные слои, не единый Auth.js provider
2. AI_SERVICE → AI_PROVIDER_ADAPTER — обязательная граница, domain-слои не видят Anthropic SDK напрямую

## D-0004 — Обычный git push — GREEN, не требует подтверждения Olga

**Дата:** 12 августа 2026
**Статус:** Принято (YELLOW — процессное решение, обратимое)

**Контекст.** После завершения Task 0.1 возник вопрос: должен ли обычный `git push` (без force) после закоммиченной, завершённой задачи каждый раз ждать явного подтверждения Olga, или это часть штатного Definition of Done. Olga явно решила: не должен.

**Решение:** обычный `git push` без `--force` в конце завершённой и закоммиченной задачи — **GREEN**. Выполняется как часть Definition of Done, без запроса подтверждения.

Подтверждение Olga обязательно только для:
1. force push (`--force`, `--force-with-lease`) или переписывания истории (`rebase`, `filter-branch` и т.п.) на уже опубликованных коммитах,
2. push, затрагивающего что-либо за пределами кода коммита — релизы, теги, production-конфигурацию, деплой-триггеры.

Зафиксировано в `CLAUDE.md` §4.1.

**Последствия:** обычные task-коммиты пушатся в конце задачи автоматически, без паузы на подтверждение. Это ускоряет соло-разработку и не создаёт риска — repository history остаётся линейной, необратимых операций в GREEN-случае нет. Любая операция, попадающая под п.1 или п.2 выше, по-прежнему требует явного разрешения Olga.

## D-0005 — `npm audit fix --force` не выполняется автоматически

**Дата:** 12 августа 2026
**Статус:** Принято (YELLOW — техническое, обратимое; подтверждено ChatGPT при review завершения Task 0.2)

**Контекст.** При верификации Task 0.2 (`npm install`) `npm audit` показал 3 high severity уязвимости — транзитивные зависимости `postcss` и `sharp` через Next.js 15. `npm audit fix --force` предлагает автоматическое исправление, но оно означает мажорный апгрейд `next` 15 → 16 (breaking change).

**Решение:** автоматический `--force`-фикс не выполняется. Смена мажорной версии фреймворка — архитектурное/версионное решение, требующее отдельного исследования (breaking changes Next.js 16, миграция App Router, совместимость с уже написанным кодом слоёв), а не побочный эффект рутинной проверки зависимостей. Уязвимости зафиксированы как Known Issue в `CURRENT_STATUS.md` и `CHANGELOG.md` — не блокируют Phase 0.

**Последствия:** апгрейд на Next.js 16 остаётся отложенной задачей до отдельного решения Olga (когда и в рамках какой задачи). До этого момента `npm audit` будет показывать эти 3 уязвимости при каждой проверке — это ожидаемо, не повод для повторного разбирательства без нового контекста.

## D-0006 — Смена GitHub-аккаунта/репозитория (RED-действие, выполнено лично Olga)

**Дата:** 12 августа 2026
**Статус:** Принято (RED — продуктовое/владельческое решение, не техническое; зафиксировано постфактум)

**Контекст.** В процессе работы над Task 0.4 push в исходный репозиторий (`Olgavladimirovna83-create/Application`) начал падать из-за нехватки scope `workflow` у сохранённого в macOS Keychain personal access token. ## D-0009 — Task 2.1: механизм аутентификации MVP — Credentials (email+password), не OAuth/magic link

**Дата:** 12 августа 2026
**Статус:** Принято (YELLOW — техническая развилка, явно делегированная Olga на этап реализации `30_SECURITY_PRIVACY.md` §6, с одним заранее заданным ограничением)

**Контекст.** `30_SECURITY_PRIVACY.md` §6 не фиксирует конкретный механизм аутентификации для MVP («OAuth; token-based authentication; passwordless authentication... Конкретный механизм определяется на этапе реализации»). Перед началом Task 2.1 Olga заранее задала ограничение: если выбранный механизм требует внешнего email-сервиса для отправки писем (magic link, email-верификация — например через Resend, SendGrid) — это создание нового внешнего аккаунта/авторизации, то есть **RED** по той же логике, что уже применялась к смене GitHub-аккаунта (D-0006) и к облачной инфраструктуре Vercel/Neon/Upstash/R2 (D-0007): агент обязан остановиться и спросить, не создавать такой аккаунт самостоятельно.

**Решение.** Реализован **Credentials provider** (email + password, `next-auth` v5 / Auth.js) — не OAuth, не magic link, не email-верификация. Обоснование:
- Не требует никакого внешнего сервиса (email-провайдера, OAuth-провайдера) и, соответственно, не создаёт RED-ситуацию с новым внешним аккаунтом — прямое следствие ограничения, заданного Olga.
- Полностью реализуется существующим стеком (`next-auth`, `@auth/prisma-adapter`, `bcryptjs` для хеширования паролей) без новых внешних зависимостей.
- Соответствует духу `30_SECURITY_PRIVACY.md` §6–9: пароли не хранятся в открытом виде (`bcryptjs`, 12 salt rounds), проверка — на backend (`authenticateWithCredentials`), не доверяется frontend.
- Ограничение: Credentials provider несовместим с database-сессиями Auth.js (Prisma adapter не пишет сессии для Credentials-логина по архитектуре Auth.js) — используется **JWT session strategy** (`session: { strategy: 'jwt' }`). Это верифицировано через актуальную документацию authjs.dev (WebFetch на момент реализации), а не только по памяти — учитывая, что схема аутентификации критична для security, ошибка в этом месте дорого стоит.
- `PrismaAdapter(prisma)` в `src/auth/config.ts` — единственное осознанное исключение из правила «только `prismaClient.ts` работает с `@prisma/client` напрямую» (CLAUDE.md §3.1/§4.1): контракт стороннего адаптера Auth.js требует передать ему сырой `PrismaClient`-инстанс, это не наш обычный data-access паттерн и не повод создавать сквозной доступ к Prisma в другом коде.
- Поле `passwordHash` на модели `User` — наше собственное поле, не часть контракта `@auth/prisma-adapter` (в отличие от `email`/`emailVerified`/`name`/`image`, которые заданы контрактом адаптера буквально).

**Явно не входит в Task 2.1** (см. `TASKS.md`): UI/API для registration/login/logout, account recovery, authorization/roles, полный HTTP sign-in flow (issuance cookie-based JWT-сессии в браузере) — только сама техническая основа (schema + `authenticateWithCredentials` + Auth.js конфигурация), проверенная integration-тестом уровня функции, не уровня HTTP.

**Последствия.** Registration/login UI (следующие задачи Phase 2) будет собирать email+password напрямую, без redirect на внешний OAuth-провайдер и без email-верификации на этом этапе. Если в будущем потребуется magic link, email-верификация или OAuth (Google/etc.) — это отдельная задача, которая снова столкнётся с тем же RED-ограничением (внешний email-сервис или OAuth-провайдер = новый внешний аккаунт) и потребует отдельного разрешения Olga, а не тихого добавления провайдера. Password reset (обычно требует email) в Phase 2 пока не расписан по той же причине — будет отдельной задачей, когда до неё дойдёт очередь, и снова возможной RED-точкой.

## D-0010 — Известный security-gap: access token `ExternalAccount` хранится без encryption at rest (закрыть до production)

**Дата:** 13 августа 2026
**Статус:** Принято сознательно, как временный gap (YELLOW по факту реализации, но зафиксирован по прямому требованию Olga — не тихий пропуск)

**Контекст.** Task 3.3 вводит модель `ExternalAccount` (`25_DATABASE_SCHEMA.md` §7) для хранения подключения Instagram-аккаунта, включая сам access token (поле `accessToken`) и срок его действия (`tokenExpiresAt`) — эти два поля практически необходимы, хотя и не входят буквально в перечень полей §7. `30_SECURITY_PRIVACY.md` §22–24 прямо требует для credentials внешних платформ: хранение отдельно от обычных пользовательских данных (§22 — выполнено, отдельная таблица), **encryption at rest** (§23 — **не выполнено**), и token rotation, где поддерживается провайдером (§24 — Instagram поддерживает `refresh_access_token`, механизм ротации реализован в `IntegrationProvider.refreshTokens`, Task 3.1/3.2, но сама ротация ещё не подключена ни к одной sync-джобе — это отдельная будущая задача).

**Решение.** `ExternalAccount.accessToken` хранится в Postgres обычным текстовым полем (`String`, DB-тип `TEXT`), **без шифрования**. Это осознанный, явно зафиксированный gap, не молчаливое упущение — Olga потребовала зафиксировать его именно так перед реализацией Task 3.3, а не после.

**Обоснование (почему сейчас, а не блокировать Task 3.3 до устранения):**
- Encryption at rest для конкретного поля в Postgres реалистично требует либо: (a) отдельного secret manager / KMS для хранения ключа шифрования отдельно от данных (`30_SECURITY_PRIVACY.md` §23 — «ключи шифрования не должны храниться рядом с зашифрованными credentials»), либо (b) `pgcrypto`/application-level encryption с ключом из env — оба варианта требуют инфраструктуры, которая **сознательно отложена вместе со всем остальным cloud-стеком** (Vercel/Neon/Upstash/R2, secret manager) решением Olga, см. D-0007. Реализовывать шифрование сейчас означало бы либо тащить в Task 3.3 кусок отложенной инфраструктуры (расширение scope без разрешения), либо городить одноразовый локальный workaround (например AES с ключом из `.env`), который создал бы ложное чувство защищённости, не решая задачу по-настоящему (ключ шифрования лежал бы в том же `.env`, что и сами данные — прямое нарушение той же самой §23).
- MVP на этом этапе работает с одним реальным подключённым аккаунтом (тестовый аккаунт Olga), локальная dev-база, не production — риск от отсутствия шифрования сейчас несопоставим с риском в production со множеством реальных пользователей.

**Явная зарубка на будущее (обязательно закрыть до production, не забыть):**
- Прежде чем открывать реальным пользователям возможность подключать Instagram (сейчас это возможно только вручную, диагностический callback route, не production UI) — `ExternalAccount.accessToken` должен быть зашифрован at rest, ключ шифрования вынесен в отдельный secret manager (после того как он появится, см. D-0007).
- Это одна из причин, по которой Advanced Access / App Review / Business Verification для реальных пользователей (`INSTAGRAM_API_REVIEW.md` §3) и production-запуск Instagram-интеграции в принципе не должны начинаться, пока этот gap не закрыт — обе зависимости (Meta App Review и encryption at rest) в любом случае блокируют реальный запуск, но каждая по своей причине, и их не стоит путать одну с другой.

**Последствия.** Никаких изменений в реализации Task 3.3 сверх того, что уже сделано — только явная фиксация здесь, чтобы gap не потерялся между задачами. Любая будущая задача, которая приближает продукт к реальному запуску (App Review, публичный UI для подключения аккаунтов), должна явно сверяться с этим решением перед стартом.

## D-0011 — Task 4.1: сырой ответ Instagram API не сохраняется отдельно на этом этапе — только нормализованные данные

**Статус:** Принято (YELLOW — открытый вопрос, который Olga явно попросила решить и зафиксировать перед стартом Task 4.1, не оставлять неявным)

**Контекст.** `26_DATA_PIPELINE.md` §4 (RAW_DATA) рекомендует по возможности сохранять исходные данные до преобразования — для повторной обработки, исправления ошибок, новой аналитики, аудита и сравнения версий pipeline («Система **должна по возможности** сохранять» — не жёсткое «обязана всегда»). Task 4.1 (первая задача Phase 4 — Ingestion Pipeline) реализует разовую синхронную синхронизацию Instagram → `Content`/`PerformanceMetric` и должна явно решить: сохранять ли сырой JSON-ответ от `getAccountInsights`/`listRecentMedia`/`getMediaInsights` отдельно от нормализованных данных, или ограничиться только нормализацией на этом этапе.

**Решение.** На этом этапе (Task 4.1) сырой ответ API **не сохраняется** отдельно. В БД попадают только нормализованные `Content`/`PerformanceMetric`. Raw payload используется только внутри самого запроса (для валидации и нормализации), после чего не сохраняется.

**Обоснование:**
- **Нет подходящего места для хранения без нового scope.** В текущей 10-сущностной схеме (Task 1.1, D-0008) нет entity под сырые payload'ы. `EVENTS` из `25_DATABASE_SCHEMA.md` §38 семантически не подходит — это лог доменных событий (`RECOMMENDATION_CREATED`, `USER_ACCEPTED` и т.п.), не хранилище сырых внешних ответов; использовать его для этого значило бы смешать два разных по смыслу назначения одной таблицы. Настоящее «сырое хранилище» — это либо новая таблица (со своими вопросами по retention/GC, которые не тривиальны и не входят в «один шаг»), либо object storage.
- **Object storage (R2) для этого физически не готов.** `ObjectStorageService`/`providers/r2.ts` существуют как код (Task 0.2), но реальный R2-бакет не создан — вся облачная инфраструктура сознательно отложена решением Olga (D-0007). Использовать R2 для сырых payload'ов сейчас означало бы либо создавать реальные cloud-ресурсы без отдельного разрешения (нарушение духа D-0007), либо городить локальную файловую замену, которую всё равно придётся переделывать.
- **Данные не теряются безвозвратно, если пропустить сейчас.** Это одноразовая ручная синхронизация одного тестового пользователя (Olga), а не production-пайплайн с множеством пользователей. Аккаунт остаётся подключённым, Instagram можно опросить повторно в любой момент, пока не истёк соответствующий период хранения на стороне платформы (`INSTAGRAM_API_REVIEW.md` §5 — до 90 дней для account-level insights). Риск «раз не сохранили сейчас — потеряли навсегда» для этого конкретного шага низкий.
- **Соответствует явной просьбе Olga** держать Task 4.1 простым и синхронным, без очереди и лишней инфраструктуры — полноценное сырое хранилище (с ретеншеном, версионированием pipeline и т.п., как описывает §4 дополнительно) больше подходит под отдельную будущую задачу, а не под первый шаг.

**Явная зарубка на будущее (не забыть, вернуться при появлении практической необходимости):**
- Когда появится реальная object storage инфраструктура (R2, после D-0007) — рассмотреть сохранение сырых ответов туда, ключ по аналогии с остальными R2-путями.
- Если/когда потребуется reprocessing (пересчёт после исправления бага в нормализации) или аудит расхождений с Instagram — это будет прямым триггером вернуться к этому решению, не откладывать бесконечно.
- Если pipeline станет scheduled/multi-user (а не ручной single-user триггер) — стоимость отсутствия raw data растёт (нельзя просто «повторить запрос вручную»), и это тоже повод пересмотреть.

## D-0012 — Forward-looking: связь «формат контента ↔ цель» не должна быть жёстко закодирована ни в коде, ни в промптах AI (важно перед Phase 6–9)

**Дата:** 13 августа 2026
**Статус:** Принято — явное продуктовое требование Olga, зафиксировано заранее как forward-looking, не блокирует текущую работу (Phase 4)

**Контекст.** Task 4.1 ввёл нормализацию формата публикации (`Content.contentType`: `image`/`video`/`carousel`/`reel`/`story`, см. `src/ingestion/normalize.ts`). Это создаёт соблазн на будущих этапах (Analysis/Knowledge/Decision/AI layers, Phase 6–9 — `29_AI_LAYER.md`, `13_RECOMMENDATION_ENGINE.md` и т.п.) закодировать в коде или в промптах для AI жёсткие правила вида «Reels — для охватов», «карусели — для сохранений» и подобные обобщённые ассоциации формата с конкретной целью.

**Решение.** Такая жёсткая привязка формата к цели **запрещена** — ни как код (например `if (contentType === 'reel') return 'reach'`), ни как часть системного промпта/инструкции для AI provider (`AI_SERVICE`/`AIProvider`, `src/ai/`). Связь между форматом контента и конкретной пользовательской целью (охваты/подписчики/сохранения/etc.) должна **вычисляться статистически, отдельно для каждого пользователя**, через уже заложенные в архитектуру механизмы:

- `GOAL_PERFORMANCE` (`18_DATA_MODEL.md` §12) — одна публикация может иметь разные результаты по разным целям одновременно (`Content A → reach: outstanding, likes: above average, saves: strong, followers: below average`); эффективность публикации принципиально не сводится к одному числу или одной предустановленной цели.
- `PATTERN`/`PATTERN_CONFIDENCE` (`18_DATA_MODEL.md` §13–16) — связь между характеристиками контента (включая формат) и результатом — это обнаруженная, confidence-based закономерность («мы подозреваем» vs «это стабильно подтверждается»), не абсолютное правило. Формируется по количеству наблюдений, повторяемости, согласованности, свежести — индивидуально для каждого пользователя, не как глобальная константа продукта.

**Обоснование:**
- У разных пользователей реально разная связь формата с результатом — это эмпирический факт, а не гипотеза: то, что работает на охваты у одного аккаунта, может лучше работать на сохранения у другого (разная аудитория, ниша, история публикаций). Жёсткое правило «Reels = охваты» было бы прямым нарушением `CLAUDE.md` §3 «permanent patterns» — запрещённого антипаттерна («закономерность считается вечной») — только применённого не ко времени, а сразу ко всем пользователям одновременно.
- Это прямое следствие уже принятой архитектуры (`GOAL_PERFORMANCE`/`PATTERN` не изобретаются сейчас — они уже описаны в `18_DATA_MODEL.md` с самого начала проекта), а не новое ограничение — фиксируется явно именно потому, что реализация Content-нормализации (Task 4.1) создаёт первый реальный соблазн срезать угол на будущих этапах, когда до Analysis/AI layers дойдёт очередь.
- Касается в равной степени и обычного кода (Decision Engine, scoring), и AI-промптов (`AI_SERVICE` не должен получать system prompt вида «Reels обычно работают на охваты» как готовый факт — максимум как одну из гипотез, которую AI использует наравне с проверенными `Pattern`, не взамен них).

**Последствия.** Ничего не меняется в реализации сейчас (Phase 4 не содержит Analysis/AI-логики). Обязательна сверка с этим решением при реализации Pattern Detection (Phase 7, Knowledge Layer) и Recommendation Engine/AI Layer (Phase 8–9) — при проектировании scoring-логики или AI-промптов, которые как-либо связывают формат контента с конкретной целью, нужно явно убедиться, что связь выводится из `Pattern`/`GOAL_PERFORMANCE` конкретного пользователя, а не захардкожена как продуктовая константа.

## D-0013 — `Content.contentType` держит `'reel'` отдельно от `'video'`, вопреки иллюстративному примеру `26_DATA_PIPELINE.md` §9

**Дата:** 13 августа 2026
**Статус:** Принято — явное продуктовое решение Olga, сознательное отклонение от примера в §9, не оплошность реализации

**Контекст.** При перепроверке цитаты `08_METRICS_FRAMEWORK.md` §4 (см. `CHANGELOG.md`/`TASKS.md`, ссылка исправлена отдельно) обнаружено смежное расхождение: `26_DATA_PIPELINE.md` §9 (NORMALIZATION) приводит пример `video / reel / short_video → video` — то есть схлопывание Reels в общий канонический тип `video`. `18_DATA_MODEL.md` §5 (CONTENT_ITEM) при этом не упоминает `reel` явно среди типов (`photo`/`video`/`carousel`/«другие форматы в будущем»). Текущая реализация (`src/ingestion/normalize.ts`, `normalizeContentType`, Task 4.1) делает противоположное — намеренно сохраняет `'reel'` как отдельное значение `Content.contentType`, отличное от `'video'`.

**Решение.** `'reel'` остаётся отдельным значением `contentType`. Код (`normalize.ts`) не меняется. Комментарий в `normalize.ts`, ранее ссылавшийся на неточную цитату `08_METRICS_FRAMEWORK.md` §4, обновлён, чтобы не создавать впечатление, что реализация следует примеру §9.

**Обоснование:**
- §9 `26_DATA_PIPELINE.md` — иллюстративный пример общего принципа нормализации («разные внешние названия могут преобразовываться в единую сущность»), не закрытый список целевых типов и не жёсткое предписание специфично для Reels.
- §5 `18_DATA_MODEL.md` явно оставляет список форматов открытым («другие форматы в будущем») — не исключает `reel` как отдельный тип, наоборот, предполагает расширяемость.
- Главное: цель Pattern Detection (Phase 7, `18_DATA_MODEL.md` §13–16 PATTERN/PATTERN_CONFIDENCE, см. [[D-0012]]) требует отличать Reels от обычного видео как разные форматы — иначе невозможно обнаружить закономерности вида «у конкретного пользователя Reels работают на охваты сильнее, чем обычное видео». Если бы Reels схлопывались в `'video'` уже при нормализации, эта информация была бы безвозвратно потеряна на этапе ingestion, и ни один более поздний слой (Analysis/Knowledge) не смог бы её восстановить.
- Подтверждено живыми данными Task 4.1: реальный аккаунт Olga вернул `media_product_type: "REELS"` для нескольких публикаций — различие реально присутствует в данных, не гипотетическое.

**Последствия.** Ничего не меняется в текущей реализации — `normalizeContentType` уже делает это правильно (Task 4.1), уточнён только комментарий. Обязательна сверка с этим решением (вместе с [[D-0012]]) при реализации Pattern Detection (Phase 7) — `reel` должен участвовать как отдельная категория формата в `PATTERN`/`GOAL_PERFORMANCE`-анализе, не сливаться с `video`.

## D-0014 — Task 4.2: новая сущность `AccountSnapshot` для account-level метрик — пробел в документированной схеме, не только в реализации

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — Olga явно попросила решить и зафиксировать перед реализацией, не оставлять неявным)

**Контекст.** `getAccountInsights` (Task 3.1–3.2) забирает account-level метрики Instagram (`08_METRICS_FRAMEWORK.md` §2 — total followers, follower growth, total reach, accounts engaged и т.п., явно отдельная категория от publication-level метрик). Task 4.1 сознательно оставил их непersistентными — только в summary синхронизации (явная scope-граница, зафиксированная в `TASKS.md`). При проработке Task 4.2 выяснилось: ни одна из существующих 10+ сущностей (Task 1.1, D-0008 + `ExternalAccount`, Task 3.3) не подходит для их постоянного хранения:
- `PerformanceMetric` — `contentId` обязателен (`25_DATABASE_SCHEMA.md` §13/§14 PERFORMANCE/PERFORMANCE_SNAPSHOTS), обе документированные сущности жёстко привязаны к публикации, account-level метрика в принципе не имеет `content_id`.
- `Baseline` (`25_DATABASE_SCHEMA.md` §16 BASELINES) — по полям (`sample_size`, `confidence`, `calculation_version`) это явно **вычисленное** значение (среднее/норма для сравнения), а не сырое измерение с платформы. Использовать его для сырых снимков означало бы смешать два разных по смыслу понятия в одной таблице.

Это реальный пробел в документированной схеме (`25_DATABASE_SCHEMA.md` не описывает ни одной сущности под сырые account-level измерения), не только пробел в объёме Task 4.1 — зафиксирован отдельно в `DOCUMENT_CROSS_REFERENCE.md` («Известные ограничения»), чтобы не пришлось переоткрывать при следующей задаче, которая коснётся account-level данных.

**Решение.** Новая сущность `AccountSnapshot` — по аналогии с `PerformanceMetric`, но на уровне `ExternalAccount` вместо `Content`:
- `id`, `externalAccountId` (→ `ExternalAccount`, `onDelete: Cascade`), `metricType`, `value` (nullable `Int`), `capturedAt`, `source`, `createdAt`.
- Snapshot-семантика (как `PerformanceMetric`, `26_DATA_PIPELINE.md` §19 SNAPSHOT_PRINCIPLE): каждый sync создаёт **новые** строки, не upsert — временной ряд, не текущее состояние.
- `value` nullable — тот же принцип NULL vs ZERO (`25_DATABASE_SCHEMA.md` §56), `unavailableMetrics` из `getAccountInsights` тоже сохраняются как `value: null` строки, не пропускаются молча (`08_METRICS_FRAMEWORK.md` §11).
- Вызывается из уже существующего `syncInstagramAccount` (`src/ingestion/instagramSync.ts`) сразу после получения `getAccountInsights`, тем же синхронным путём, без новой инфраструктуры.

**Обоснование:**
- Минимальный риск: копирует уже проверенный, работающий паттерн `PerformanceMetric`, а не изобретает новую модель хранения метрик.
- Не смешивает сырое измерение с вычисленным значением — сохраняет чёткое разделение, которое уже подразумевает документированная схема (raw `PerformanceMetric`/`PERFORMANCE_SNAPSHOTS` vs derived `Baseline`/`BASELINES`), просто закрывает пробел на account-level стороне тем же принципом.
- `capturedAt`, а не `measuredAt` — по прямому указанию Olga, совпадает с терминологией `25_DATABASE_SCHEMA.md` §14 PERFORMANCE_SNAPSHOTS (`captured_at`), которая ближе по смыслу (snapshot во времени), чем §13 PERFORMANCE, откуda исторически взято имя поля `PerformanceMetric.measuredAt`.

**Последствия.** Новая таблица `account_snapshots`, миграция `20260813191441_account_snapshots`, применена и проверена на чистое переприменение полной истории (5 миграций) на одноразовой базе. `docs/25_DATABASE_SCHEMA.md` не редактируется (read-only источник истины, `CLAUDE.md` §2) — пробел зафиксирован в `DOCUMENT_CROSS_REFERENCE.md`, не в `/docs`. Обязательно учитывать `AccountSnapshot` как источник account-level данных при проектировании `Baseline`-вычислений и Pattern Detection (Phase 6–7), когда до них дойдёт очередь — сырые данные и вычисленные из них величины теперь физически разделены, как и задумано документированной схемой для content-level данных.

## D-0015 — Task 5.1: `SyncWarning` (Task 4.3) не персистится — data quality status опирается только на `ExternalAccount.status` как сигнал сбоя

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** Olga попросила свести в статус «состояние данных» три существующих источника: `ExternalAccount.lastSyncedAt`/`status`, `AccountSnapshot`/`PerformanceMetric` timestamps и `SyncWarning` из Task 4.3. При реализации выяснилось: `SyncWarning` существует только как значение, которое `syncInstagramAccount` возвращает вызывающему коду за один конкретный вызов (`POST /api/integrations/instagram/sync` → JSON-ответ → `SyncButton.tsx`). Нигде не сохраняется — ни в БД, ни во временном хранилище. Функция data quality status, читающая состояние независимо от момента последнего клика «Синхронизировать» (например, при открытии дашборда часы или дни спустя), физически не может увидеть warnings прошлых синхронизаций — их больше не существует к моменту чтения.

**Решение.** «Были ли недавние сбои» в `getDataQualityStatus` (`src/dataQuality/dataQualityStatus.ts`) отвечает единственный персистентный сигнал — `ExternalAccount.status === 'expired'` (`hasRecentFailure`). Per-item/account-insights warnings (retry-исчерпание, невалидные media-записи и т.п.) в статус не попадают — не потому что неважны, а потому что физически недоступны на момент чтения.

**Обоснование:**
- Это находка, сделанная при формулировке задачи, не решение оставить `SyncWarning` неиспользованным намеренно с самого начала — Olga явно назвала его как источник, ожидая, что он доступен для чтения.
- Безопасный вариант — не потерять данные молча, а явно задокументировать, что источник недоступен, и использовать единственный реально персистентный сигнал сбоя вместо того, чтобы либо (а) тихо проигнорировать этот пункт запроса, либо (б) начать без разрешения проектировать новую персистентную историю sync-попыток, которая не была частью "не собирать новые данные, свести уже существующее".
- Персистентная история sync-попыток (нужна, если понадобится больше, чем текущий статус — например Pattern Detection на "как часто sync проваливается") — реальный, но отдельный будущий кандидат, не блокирует Task 5.1.

**Последствия.** `AccountDataQualityStatus.hasRecentFailure` отражает только терминальное состояние токена (`expired`), не полную историю предупреждений. Если в будущем понадобится более точная картина сбоев (например для UI-индикатора «последний sync прошёл с ошибками X дней назад»), потребуется отдельная задача — добавить персистентное поле на `ExternalAccount` (например `lastSyncOutcome`/`lastSyncWarningsCount`) или отдельную таблицу истории синхронизаций, обновляемую внутри `syncInstagramAccount`.

## D-0016 — Task 5.2: sync count anomaly детектируется через кластеризацию `PerformanceMetric.measuredAt` по разрыву во времени — точных границ sync run в схеме нет

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** Olga попросила простую проверку на аномалию: если последняя синхронизация вернула заметно меньше записей, чем обычно для аккаунта — сравнение с историей, не абсолютный порог. В схеме нет отдельной сущности «sync run» — ни `syncInstagramAccount`, ни что-либо ещё не сохраняет явную границу «это результат вызова №N». Единственный follow-through — `PerformanceMetric.measuredAt`, который в `instagramSync.ts` вычисляется как `new Date()` один раз на публикацию внутри цикла: строго одинаков для всех метрик одной публикации в одном sync, но отличается на доли секунды между разными публикациями того же sync (время на HTTP-вызовы между ними).

**Решение.** Границы прошлых sync-прогонов восстанавливаются приближённо: временные метки сортируются, соседние группируются в один «прогон», если разрыв между ними не превышает `SYNC_RUN_GAP_MS` (5 минут, заглушка — см. комментарий в `anomalyDetection.ts`, тот же характер, что `STALE_AFTER_MS` в Task 5.1). Аномалия — когда количество различных `contentId` в последнем прогоне меньше `ANOMALY_RATIO_THRESHOLD` (0.5) от среднего по всем предыдущим прогонам того же аккаунта. Если прогон всего один — статус `insufficient_history`, не ложный «ok»/«anomaly».

**Обоснование:**
- Точная альтернатива (персистентная сущность «sync run» — id, время начала, число обработанных записей) — это новые данные сверх того, что уже сохранено, а Olga явно попросила Task 5.2 «полностью на уже сохранённых данных», продолжая принцип Task 5.1 «не собирать новые данные». Кластеризация — единственный способ ответить на вопрос без нарушения этого требования.
- Относительный порог (доля от среднего), а не абсолютное число записей — прямое требование Olga, и оно же корректно ведёт себя для аккаунтов разного размера (проверено юнит-тестом: 2 из обычных 3 не считается аномалией, тогда как абсолютный порог вроде «меньше 5» ошибочно сработал бы на маленьком аккаунте).
- 5-минутный разрыв — практическая оценка: один sync (даже с retry/backoff из Task 4.3, до 3 попыток на публикацию) на аккаунте из ~25 публикаций укладывается в секунды — де-факто заведомо меньше 5 минут между соседними публикациями одного прогона, но заведомо меньше паузы, которую сделал бы человек между двумя осознанными нажатиями «Синхронизировать».

**Последствия.** Это приближение, не точный подсчёт — на очень медленном или очень длинном sync (много retry-исчерпаний подряд) два соседних progона того же реального вызова теоретически могут быть ошибочно разделены на два «прогона» в кластеризации. При текущем масштабе (единичный ручной пользователь, ~25 публикаций, sync занимает секунды) риск практически нулевой. Если аномалия станет чаще ложно срабатывать/не срабатывать на практике — правильное решение не подкручивать `SYNC_RUN_GAP_MS`, а добавить персистентную сущность sync run (см. также зарубку в D-0015 про историю sync-попыток) — это будущая задача, не Task 5.2.

## D-0019 — Task 6.2: personal baseline вычисляется на лету (scope: global, без персистентности/версионирования); confidence по объёму выборки — пороги-заглушки

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** `25_DATABASE_SCHEMA.md` §16 BASELINES описывает персистентную сущность: `baseline_id`/`user_id`/`metric`/`scope`/`scope_value`/`value`/`sample_size`/`confidence`/`calculated_at`/`calculation_version`, где `scope` может быть `global`/`format`/`topic`/`goal`/комбинацией признаков; §17 BASELINE_HISTORY требует не уничтожать предыдущие версии при пересчёте. Olga явно попросила «простой personal baseline… полностью на уже сохранённых данных» — не создание новой персистентной сущности, а расширение уже существующего (Task 6.1) вывода.

**Решение.**
1. Baseline **не персистится** — вычисляется заново при каждом вызове (`computeBaseline`, `personalBaseline.ts`), тот же принцип, что весь Task 6.1: ничего не сохраняется сверх `Content`/`PerformanceMetric`. `calculatedAt` (§14 BASELINE_VERSION — «версия или дата расчёта») присутствует как момент вызова, не как версия персистентной записи.
2. Только `scope: global` — среднее по **всем** сохранённым публикациям пользователя (не ограничено периодом, не сегментировано по формату/теме/цели). Полноценные non-global scope из §16 — будущая задача, не эта.
3. `confidence` — три уровня (`low`/`medium`/`high`) по объёму выборки: `< 5` → `low`, `5–14` → `medium`, `15+` → `high`. Итоговый confidence сравнения — минимум из двух confidence (baseline и текущего периода), не confidence одного baseline: сравнение ненадёжно, если ненадёжно ЛИБО прошлое, ЛИБО настоящее, даже если другая сторона надёжна.

**Обоснование:**
- Полноценная персистентная `Baseline`-сущность с историей версий (§16/§17) — заметно больший шаг (новая Prisma-модель, миграция, семантика non-global scope, retention для истории версий), чем «простой baseline… один шаг», который просила Olga. Компромисс тот же, что Task 6.1 в целом: вычисляемое knowledge, не сохранённый факт (§13 PERSONAL_BASELINE — «baseline является вычисляемым знанием, а не исходным фактом» — это буквально то же самое утверждение, которое оправдывает и его непостоянство здесь).
- Порог `< 5` — прямо в духе просьбы Olga «не выдавай уверенный вывод на 2-3 постах»: 5 заведомо выше её ориентира «2-3», с запасом. `15+` для `high` — тоже заглушка, не измеренная величина (тот же характер, что `TREND_CHANGE_THRESHOLD`/`ANOMALY_RATIO_THRESHOLD`).
- Минимум из двух confidence, а не confidence одного baseline — иначе возможна ложная уверенность: надёжный baseline (20 публикаций истории) сравнивается с периодом из 2 постов — само сравнение в этом случае всё равно ненадёжно, хотя baseline сам по себе «high». Явно протестировано (`personal-baseline.test.ts`, `account-analytics.smoke.test.ts`).

**Последствия.** При появлении реальной потребности в non-global scope (сравнение по формату/теме — естественное продолжение, когда дойдёт очередь до Pattern Detection, Phase 7) или в истории версий baseline (например для объяснимости прошлых рекомендаций, `CLAUDE.md` §3 — Recommendation → Reason → Pattern → Evidence) потребуется отдельная задача с персистентной `Baseline`-моделью — не расширение этой функции задним числом.

Пересмотреть семантику (переход на деление по календарной середине периода, `(period.start.getTime() + period.end.getTime()) / 2`, а не по индексу отсортированного массива) обязательно **до того**, как на `trend` начнёт опираться Recommendation Engine (Phase 8) — момент, когда неточность тренда перестаёт быть безобидной deталью реализации и становится источником ошибочных рекомендаций.

**Последствия.** Не создаёт технического долга, требующего немедленного внимания — только зарубка на будущее. Проверить эту зарубку явно перед началом Phase 8 (наравне с уже существующими зарубками D-0008/D-0012/D-0013/D-0015/D-0016/D-0017/D-0018/D-0019, проверяемыми перед Phase 7/8).

**Обоснование:**
- Формальные evidence references потребовали бы новой сущности (`MemoryEvidence`, миграция, семантика связи с `Content`/`Pattern`/будущим `Recommendation`) — заметно больше, чем «первый шаг» Knowledge Layer. `outcome`/`relevance` пока не имеют смысла для сырого аналитического факта — они относятся к цепочке `Recommendation → Reason → Pattern → Evidence → Content → Performance` (`CLAUDE.md` §3), которой ещё не существует (Decision/AI layers — Phase 8+). Реализовывать поля, которым нечем ещё наполниться, было бы преждевременным усложнением.
- Фиксированная шкала confidence проще и честнее, чем изобретать псевдо-точный вероятностный расчёт из категориальной оценки, у которой изначально нет статистической калибровки (пороги D-0019 сами по себе — заглушки объёма выборки, не измеренные величины).

**Последствия.** `Memory`-записи Task 7.1 — частичная реализация §35, не полная. Формальные evidence references — реальный кандидат на будущую задачу, когда Decision Engine/Recommendation (Phase 8) начнёт опираться на конкретные `Memory` записи и понадобится восстанавливать цепочку `Recommendation → Reason → ... → Evidence` программно, а не текстовым описанием внутри `content`. Числовая шкала confidence подлежит пересмотру, если понадобится более точная градация, чем три уровня.

## D-0023 — Task 7.2: первое использование `Pattern` — гранулярность на уровне публикации, upsert (не snapshot), пороги-заглушки, §16 PATTERN_EVIDENCE не реализован

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** `26_DATA_PIPELINE.md` §28 PATTERN_DETECTION перечисляет пять видов закономерностей: повторяющиеся сильные результаты, устойчивые слабые результаты, комбинации признаков, изменения поведения, новые emerging patterns. §29 POSITIVE_PATTERN/§30 NEGATIVE_PATTERN требуют репрезентативности (не один пост → «всегда работает») и вводят для отрицательных результатов три степени (`SLIGHTLY_BELOW_BASELINE`/`CLEARLY_WEAK`/`STRONG_FAILURE`). §31 PATTERN_CONFIDENCE — confidence зависит от sample size/consistency/effect size/recency/data quality. `Pattern` (модель с Task 1.1, впервые используется здесь) — поля по `22_DATA_MODEL.md` §15: pattern_id/userId/description/связанные признаки/связанные цели/направление/силу/confidence/даты появления-подтверждения-изменения; §16 PATTERN_EVIDENCE требует формальной связи с публикациями-основаниями; §17 PATTERN_STATUS — жизненный цикл hypothesis→emerging→confirmed→strong→declining→inactive; §18 PATTERN_DECAY/§19 PATTERN_REACTIVATION — угасание confidence и повторное подтверждение одной и той же закономерности со временем.

**Решение.**
1. **Гранулярность — отдельная публикация, не период.** Каждая публикация сравнивается с personal baseline (Task 6.2) по тому же относительному порогу (10%), что и весь остальной код — прямое следствие буквальной формулировки §29 («один успешный **пост**»), не сохранённого из Task 6.2 усреднения по периоду.
2. **Только два вида закономерности из пяти в §28**: повторяющиеся сильные/слабые результаты (простая частотная закономерность на уровне метрики). Комбинации признаков (нужен `ContentFeature`, не задействован ни разу), изменения поведения во времени, ранжирование по градации `SLIGHTLY_BELOW_BASELINE`/`CLEARLY_WEAK`/`STRONG_FAILURE` (§30) — не входят.
3. **Жизненный цикл (§17/§18/§19) не реализован.** `status` не устанавливается вручную — остаётся Prisma-дефолтом `hypothesis` при создании и не меняется при обновлении. Confidence НЕ угасает, если повторный прогон не находит чёткого направления — существующий `Pattern` просто не трогается (не разрушается молча, но и не эволюционирует по документированному жизненному циклу).
4. **Upsert по `(userId, patternType)`, не snapshot.** В отличие от `PerformanceMetric`/`AccountSnapshot`/`Memory` (Task 4.1/4.2/7.1) — единственная эволюционирующая запись, не новая строка на каждый прогон. Прямое следствие §18: «старая информация не удаляется, история сохраняется» — внутри одной записи, не через накопление снимков.
5. **§16 PATTERN_EVIDENCE не реализован формально** — тот же класс пробела, что `MEMORY_EVIDENCE` в Task 7.1 (D-0022): basis описывается текстом в `description` («N из M публикаций выше нормы»), не связью с конкретными `Content`.
6. **Пороги — заглушки**: `MIN_OBSERVATIONS_FOR_PATTERN = 5` (тот же порядок, что D-0019/Task 6.2 — не создавать вывод на 2–3 постах), `ITEM_COMPARISON_THRESHOLD = 10%` (тот же порог, что тренд/сравнение с baseline везде в кодовой базе), `MIN_CONSISTENCY_FOR_PATTERN = 60%` (простое большинство недостаточно — специально проверено тестом на ровно 50/50 распределении, направление не определяется). Confidence переиспользует шкалу объёма выборки из Task 7.1 (`CONFIDENCE_SCORE`, `personalBaseline.ts`), умноженную на consistency.

**Обоснование:**
- Полная реализация §28 (все пять видов) + §17–19 (полный жизненный цикл) + формальные evidence references — это не «один шаг», а вся тема Pattern Detection целиком, прямо против явного требования Olga. Выбран самый простой содержательный срез: частотная закономерность по каждой из трёх уже собираемых метрик, с честной, проверяемой оценкой уверенности.
- Upsert, а не snapshot — не implementation-деталь на усмотрение, а прямое следствие документированной семантики Pattern (§18: «старая информация не удаляется» — про одну эволюционирующую запись, не про накопление истории снимков, как у `PerformanceMetric`). Ошибиться в эту сторону означало бы противоречить документу, не просто недоделать его.
- Порог консистентности 60%, а не просто «большинство» (>50%) — предотвращает создание закономерности из практически случайного распределения (51/49), что было бы прямым нарушением духа §29 («один успешный пост не создаёт закономерность») применённого к почти равному разбросу, а не к единичному случаю.

**Последствия.** Реализация Task 7.2 — первый, не финальный, шаг Pattern Detection. Жизненный цикл (§17–19), комбинации признаков (§28), градация отрицательных результатов (§30), формальные evidence references (§16) — реальные, документированные, но сознательно отложенные части темы, кандидаты на Task 7.3+, не тихо забытые. Обязательно свериться с этим решением при дальнейшей работе над Pattern Detection — не считать Task 7.2 «done» по смыслу §28–31 целиком.

## D-0024 — Task 8.1: CANDIDATE_SCORER считает только 3 из 9 факторов; ranking раздельно по метрике, не единым списком; личная норма остаётся глобальной, кандидат сравнивается по формату

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** `23_SYSTEM_ARCHITECTURE.md` §26 CANDIDATE_SCORER перечисляет ровно 9 факторов: goal fit, recent performance, historical performance, pattern strength, confidence, freshness, repetition, risk, opportunity. `21_DECISION_LOGIC.md` §39 DECISION_SCORE описывает близкий, но не идентичный список (8 положительных + 3 вычитаемых). **Уточнение цитаты, найденное при формулировке**: Olga сослалась на «§36 требует reasons/context/decision_version» для Recommendation-таблицы — при проверке `decision_version` оказался в `25_DATABASE_SCHEMA.md` §26 RECOMMENDATIONS, `reasons` — §28 RECOMMENDATION_REASONS, `context` — §30 RECOMMENDATION_CONTEXT; §36 в этом документе — MEMORY (уже обсуждалось в D-0022/D-0023 про §37 MEMORY_EVIDENCE). Похоже на перенос номера раздела из соседнего обсуждения — содержательный вывод (не писать в Recommendation, эти поля — следующий шаг) остаётся верным, поправлен только номер.

**Решение.**
1. Реализованы 3 из 9 факторов CANDIDATE_SCORER: **historical performance** (личная норма, Task 6.2, `computeBaseline`, `scope: global`, D-0019 — сознательно не меняется здесь), **сравнение конкретного кандидата с этой нормой** (новое: раньше Task 6.2/7.2 считали метрику в целом по всем форматам разом, теперь — отдельно по каждому формату, тем же порогом 10%, что и везде в коде) и **confidence** (переиспользует `compareToBaseline` без изменений). Goal fit/freshness/repetition/risk/opportunity — не реализованы, нет для них расчёта.
2. **Pattern (Task 7.2) — контекст, не отдельный вклад в ранжирование.** Pattern глобален (по метрике, не по формату) — один и тот же Pattern не может честно объяснять, почему один кандидат лучше другого. Используется только для пометки в `label`, когда направление кандидата совпадает с направлением уже подтверждённого паттерна, никогда не участвует в сортировке.
3. **Ranking — раздельно по каждой метрике** (`reach`/`likes`/`saved`), не единый список кандидатов across all metrics. Без goal fit (единственного фактора, который в документе решает, какая метрика важнее пользователю) схлопывание трёх метрик в одну оценку было бы придуманным весом — то есть само стало бы false precision (§40), только на уровне архитектуры оценки, а не отображаемого числа.
4. **Личная норма остаётся глобальной** (не пересчитывается по формату) — сравнивается с ней среднее конкретного кандидата. Это не противоречит D-0019 (baseline: global scope) — norm не сегментирована, сегментировано то, что с ней сравнивается.

**Обоснование:**
- Полная 9-факторная формула требует данных, которых физически нет: goal-matching логики (Goal не связан с метриками нигде в коде), decay/freshness-логики (не реализована ни для Pattern, ни для контента), истории рекомендаций (Recommendation-таблица не заполняется — Task 8.1 сознательно read-only), risk/opportunity-эвристик (не спроектированы). Честно посчитать 3 фактора лучше, чем притвориться, что посчитаны все 9.
- Раздельный ranking по метрике — прямое применение духа §40 NO FALSE PRECISION к архитектуре, не только к формату вывода: единый межметричный рейтинг без goal fit выглядел бы решённым, но был бы основан на невидимом произвольном весе.

**Последствия.** Когда появится goal-matching (реальная связь `Goal` → метрика/приоритет), станет возможным объединить три раздельных ranking в один — не раньше. Freshness/repetition/risk/opportunity — реальные, документированные, кандидаты на будущие задачи Phase 8, не эта. Обязательно свериться при дальнейшей работе над Decision Engine — Task 8.1 не закрывает CANDIDATE_SCORER целиком, только его read-only, частично-факторный первый срез.

## D-0025 — Task 8.2: goal fit — выбор первичной метрики, не смешивание; `Goal.priority` — меньшее число важнее; явные состояния для отсутствующих/нетрекаемых целей

**Дата:** 13 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** `21_DECISION_LOGIC.md` §6 GOAL_FIRST — цель первый фильтр. §7 GOAL_PRIORITY — у целей относительный приоритет (пример: 1. followers, 2. reach, 3. saves, 4. likes), главная цель получает больший вес, остальные продолжают участвовать. §8 FOUR_RECOMMENDATION_DIRECTIONS — четыре направления (likes/followers/saves/reach), «система определяет, какое из них сейчас наиболее актуально относительно целей». `Goal` (модель с Task 1.1: `userId`/`goalType`/`priority`/`status`) до этой задачи не использовалась ни одним кодом как список для решения — только create/read по id (`/api/goals`, тесты authorization).

**Решение.**
1. **Goal fit — выбор, не смешивание.** §8 буквально говорит «определяет, какое из НИХ [направлений] сейчас наиболее актуально» — про выбор направления среди уже посчитанных Task 8.1 per-metric рейтингов, не про синтез нового смешанного числа. Это прямое продолжение D-0024: там уже было решено, что смешивание метрик без goal fit — придуманный вес; теперь, когда goal fit есть, он используется для ВЫБОРА, не для порождения нового веса из ничего.
2. **`Goal.priority` — меньшее число важнее.** Направление поля не было установлено ни одним кодом до этой задачи. Принято по аналогии с ранжированным списком в примере §7 («1. followers» — первый номер, не наибольшее число).
3. **Явное сопоставление `goalType` → трекаемая метрика**, не прямое совпадение строк: `GOAL_TYPE_TO_METRIC = { reach: 'reach', likes: 'likes', saves: 'saved', saved: 'saved' }`. Найдено при формулировке: документ (§7/§8) называет метрику `saves`, реально собираемое поле — `saved` (Instagram API, D-0018) — та же метрика, разное словоупотребление, не разные понятия. Прямое совпадение строк тихо не нашло бы цель `saves`, хотя данные для неё есть.
4. **Явные состояния для honest edge cases** (прямое требование Olga): `no_goals_defined` (целей нет вовсе — не выбирается цель «по умолчанию», GOAL_FIRST требует цель как первый фильтр, без неё фильтровать нечем) и `no_tracked_goals` (цели есть, но ни одна не сопоставляется с трекаемой метрикой — типичный случай: `goalType: 'followers'`, followers_gained не собирается, D-0018). В обоих случаях `primaryRanking: null`, но per-metric `rankings` (Task 8.1) по-прежнему возвращаются целиком — goal fit не может выбрать первичную метрику, но не прячет остальной вывод.
5. **Fallthrough по приоритету**: если цель с наивысшим приоритетом нетрекаема, но есть цель с более низким приоритетом, которая трекается — она становится первичной (`§7`: «если целей несколько, система использует их приоритеты», «остальные цели не игнорируются»). Нетрекаемые цели выше по приоритету, чем найденная, попадают в `untrackedGoals` — явно, не молча пропущены.

**Обоснование:**
- Выбор вместо смешивания сохраняет согласованность с D-0024 — если бы Task 8.2 ввела числовое смешивание метрик по весам приоритета, это было бы ровно тем самым «придуманным весом», от которого Task 8.1 явно отказалась, только отложенным на одну задачу.
- Честные состояния `no_goals_defined`/`no_tracked_goals` — прямое требование Olga «не молчаливое предположение»: система не должна тихо считать «наверное reach» при отсутствии цели, и не должна тихо игнорировать цель `followers`, никак не сообщив, что для неё физически нет данных.

**Последствия.** Если пользователь позже определит цель для `followers`, а ingestion начнёт собирать `followers_gained` (см. зарубку D-0018), `GOAL_TYPE_TO_METRIC` нужно будет расширить — не автоматически, отдельное осознанное решение. Реальное числовое смешивание метрик по приоритету (не просто выбор одной первичной) — возможный будущий шаг, если станет практически необходим, но создаст новый риск false precision (§40) и потребует отдельного обоснования, не тихого расширения этой функции.

## D-0026 — Task 8.3: персистентность Recommendation — только при `goal_matched`, `RecommendationReason` как таблица, `context` как JSON-снимок, `decisionVersion` — первая версия-константа

**Дата:** 15 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** Olga явно ограничила scope: «сохранение в Recommendation (§26/§28/§30: reasons/context/decision_version), не добор оставшихся факторов скоринга — сначала закроем цикл "решение → можно объяснить и найти позже" на уже готовых кандидатах». `25_DATABASE_SCHEMA.md` §26 RECOMMENDATIONS перечисляет поля без списка для `context`/`reasons` как отдельных сущностей — те описаны отдельно в §28 RECOMMENDATION_REASONS (закрытый список колонок: reason_id/recommendation_id/reason_type/description/weight/confidence, словарь reason_type — pattern/performance/baseline/goal/experiment/freshness/opportunity) и §30 RECOMMENDATION_CONTEXT (описан прозой как «снимок контекста в момент создания», без фиксированного списка колонок — «может содержать»: goal/relevant baseline/active patterns/confidence/recent performance/skeleton version/decision version). `Recommendation.goalId` в схеме (Task 1.1) — обязательный (non-nullable) FK на `Goal`.

**Решение.**
1. **`RecommendationReason` — отдельная реляционная таблица**, не JSON-поле — §28 даёт явный список колонок, это соответствует структуре, уже принятой для остальных сущностей проекта (одна строка = одна причина, `@@map("recommendation_reasons")`). `reasonType` — `String`, не enum: документ приводит словарь как ориентир, не закрытый список, тот же принцип, что `goalType`/`patternType`/`metricType` (см. комментарий в начале `schema.prisma`).
2. **`context` — JSON-колонка на `Recommendation`**, не отдельная таблица — в отличие от §28, §30 не даёт фиксированного списка колонок и описан как единственный снимок на одну рекомендацию (не список строк), что структурно соответствует одной JSON-колонке, а не 1:1-таблице ради формы.
3. **Запись создаётся только при `goalFit.reason === 'goal_matched'`.** `Recommendation.goalId` обязателен — записать рекомендацию без реального `Goal.id` невозможно, а придумывать/выбирать «дефолтную» цель при `no_goals_defined`/`no_tracked_goals` было бы тем самым молчаливым предположением, которое Olga явно запретила ещё в постановке Task 8.2 (D-0025). Оба случая (и пустой/нетрекаемый ranking) возвращают явный `{ created: false, reason: ... }`, не ошибку и не запись-заглушку.
4. **`RecommendationReason.weight` не заполняется** (остаётся `null`) — ни у одного из уже посчитанных факторов (Task 8.1 D-0024, Task 8.2 D-0025) нет числового веса; заполнить колонку произвольным числом значило бы нарушить §40 NO FALSE PRECISION только потому, что в схеме есть подходящее поле.
5. **`context.skeletonVersion` — явный `null`.** «Skeleton version» не имеет референта нигде в кодовой базе (AI/prompt-слой не участвует в этом решении вовсе) — честный пробел, а не выдуманное значение, тот же принцип, что частичное покрытие `Memory` в D-0022.
6. **`DECISION_VERSION = 'decision-v1'`** — первое реальное значение `decisionVersion` (поле существовало в схеме с Task 1.1, но не заполнялось никаким кодом). Простая строковая константа текущей реализации DECISION layer (Task 8.1–8.3), не semver и не привязана к внешней схеме версионирования — такой раньше не было ни у одного значимого расчёта в проекте (`promptVersion` в `AIProvider` — параметр вызова, не внутренняя константа).
7. **Append-only, не upsert** — каждый вызов создаёт новую строку `Recommendation`, тот же принцип, что `Memory` (Task 7.1): рекомендация — событие в момент решения, на которое позже ссылаются `UserDecision`/`Outcome` (§31/§34), не текущее перезаписываемое состояние (в отличие от `Pattern`, Task 7.2, D-0023).
8. **`RECOMMENDATION_CANDIDATES` (§27) и `RECOMMENDATION_EVIDENCE` (§29) не реализованы** — Olga процитировала только §26/§28/§30, явно сузив scope; §27 (все кандидаты, участвовавшие в ranking) и §29 (формальные evidence-ссылки на content/performance/pattern/baseline) остаются задачей на будущее, не тихо пропущены — сама структура уже видна в `context.ranking` (все кандидаты primary-метрики попадают туда, только не как отдельные строки БД).

**Обоснование:**
- Условие `goal_matched` для записи — прямое продолжение честных состояний D-0025: не создавать Recommendation с фиктивным/угаданным goalId ради того, чтобы «цикл закрылся» на любом пользователе — цикл «решение → объяснимо → найдено позже» имеет смысл только для решений, которые реально были приняты (т.е. где goal fit реально выбрал метрику).
- `RecommendationReason` как таблица (не JSON) напрямую служит цепочке объяснимости из `CLAUDE.md` §3 (`Recommendation → Reason → Pattern → Evidence → Content → Performance`) — каждая причина отдельно читаема/находима, не спрятана внутри одного блока текста.

**Последствия.** `RECOMMENDATION_CANDIDATES`/`RECOMMENDATION_EVIDENCE` (§27/§29) и оставшиеся 6 из 9 факторов CANDIDATE_SCORER (freshness/repetition/risk/opportunity + числовое смешивание, D-0024/D-0025) — открытые задачи Phase 8, не покрыты этим шагом. `weight` на `RecommendationReason` останется `null`, пока не появится реальный расчёт значимости причины — заполнение его произвольным числом в будущем требует отдельного обоснования, не тихого расширения этой функции.

## D-0027 — Task 8.4: freshness + repetition как качественные сигналы CANDIDATE_SCORER, без decay-переоценки baseline и без изменения порядка ranking

**Дата:** 15 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** Olga выбрала из предложенного списка кандидатов не расширение citation scope (§27/§29), а оставшиеся факторы CANDIDATE_SCORER (`23_SYSTEM_ARCHITECTURE.md` §26) — «они напрямую улучшают качество уже работающего цикла» — и разрешила взять 1–2 фактора из 4 (freshness/repetition/risk/opportunity) за один шаг. `21_DECISION_LOGIC.md` §12 FRESHNESS_WEIGHT — «свежие данные важнее старых», буквальные пороги (0–3 месяца высокий вес / 3–6 средний / 6+ сниженный), «старая информация не удаляется, просто оказывает меньшее влияние». §13 RECENCY_OVERRIDE и §14 REPETITION_CONTROL описывают на одном и том же примере («пользователь вчера опубликовал carousel») одно и то же поведение: проверить, есть ли сейчас более эффективная альтернатива тому, что пользователь только что использовал; «если альтернативы нет, тот же формат снова может стать рекомендацией» — явно НЕ автоматическое подавление повтора. Risk (§26 RISK)/opportunity (§27 OPPORTUNITY) требуют понятия «experimental candidate»/hypothesis status (explore/exploit, §22–25), которого в текущей реализации нет — решено оставить их вне scope этого шага, не тихо пропустить: см. «Последствия».

**Решение.**
1. **Freshness и repetition реализованы как качественные СИГНАЛЫ на `CandidateResult`, не как переоценка ranking'а.** `CandidateResult.freshness: 'recent' | 'aging' | 'stale' | null` — метка по буквальным порогам §12, применённая к дате самой свежей публикации, вносящей значение в конкретного кандидата (не ко всей истории). `CandidateResult.repetitionNote: string | null` — заполняется ТОЛЬКО на топ-кандидате ranking'а метрики, и только когда он совпадает с форматом, опубликованным последним по времени (по всем форматам, `candidateGenerator.mostRecentContentType`), И есть конкурентная альтернатива (следующий по рангу кандидат не хуже `at_baseline`). Порядок `ranking` не меняется ни в одном случае — freshness/repetition не становятся дополнительным слагаемым скрытого веса, тот же принцип §40 NO FALSE PRECISION, что уже применён к Pattern (D-0024) и goal fit (D-0025).
2. **FRESHNESS_WEIGHT НЕ реализован как decay-переоценка `computeBaseline`.** §12 буквально описывает взвешивание ИСТОРИЧЕСКИХ ДАННЫХ при расчёте нормы — это означало бы менять Task 6.2 (`computeBaseline`, `scope: global`, D-0019, простое невзвешенное среднее по всей истории). Переоценка самого расчёта baseline — отдельное, более крупное архитектурное решение (затрагивает ANALYSIS layer, не только DECISION), сознательно не делается тихо внутри узкого шага Phase 8; зафиксировано как открытая задача.
3. **§13/§14 реализованы одним механизмом**, не двумя отдельными факторами — сами разделы документа описывают одно поведение с двух сторон (пример идентичен). Конкурентность альтернативы определена как: сравнение runner-up не хуже `at_baseline` (не `below`/`insufficient_data`) — не «что угодно на втором месте».
4. **`repetitionNote` НЕ становится формальной `RecommendationReason`.** Словарь `reasonType`, который перечисляет сам документ (§28: pattern/performance/baseline/goal/experiment/freshness/opportunity), не содержит «repetition» — изобретать новую категорию вместо буквального следования документу здесь не оправдано. `freshness`, наоборот, реально есть в словаре и реально посчитан — `recommendationPersistence.ts` (Task 8.3) дополнен `reasonType: 'freshness'`-причиной (confidence `null` — категориальный бакет по возрасту данных, не вероятностная оценка, тот же принцип, что 'goal').
5. **Risk/opportunity — вне scope, явно, не тихо.** Требуют «experimental candidate»/hypothesis status и explore/exploit логики (§22–25), которых нет ни в схеме (`Experiment`-модель существует с Task 1.1, но не используется ни разу ни одним кодом), ни в текущем CANDIDATE_GENERATOR/SCORER. Реализовать их честно значило бы сначала спроектировать этот статус — больше одного узкого шага.

**Обоснование:**
- Качественные сигналы, не переранжирование — прямое продолжение D-0024/D-0025: если бы freshness/repetition меняли порядок `ranking` напрямую, это было бы придуманным весом («насколько важнее свежее, чем above/below baseline?») без документированного ответа — то же нарушение §40, которого весь Phase 8 сознательно избегал.
- Использование только словаря `reasonType`, буквально данного документом (§28), а не расширение его по необходимости — тот же принцип, что не выдумывать `weight` (D-0026): лучше честно не завести причину `repetition`, чем изобрести категорию, которой нет в спецификации.

**Последствия.** FRESHNESS_WEIGHT как decay-переоценка `computeBaseline`/личной нормы (Task 6.2, D-0019) остаётся открытой задачей — потребует отдельного решения о том, как совмещать с уже принятым `scope: global`. Risk/opportunity (§26 RISK/§27 OPPORTUNITY) остаются нереализованными факторами CANDIDATE_SCORER — нужен «experimental candidate»/hypothesis status как предварительный шаг. `Experiment`-модель (Task 1.1) по-прежнему не используется ни одним кодом — первое реальное использование, вероятно, состоится вместе с risk/opportunity.

## D-0028 — Task 9.1: первый реальный AI-запрос (decision explanation) — качественный confidence в промпте, AiRun как отдельная append-only лог-таблица, DI-параметр вместо мока AIService

**Дата:** 15 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9)

**Контекст.** Olga сформулировала Task 9.1 узко и с конкретными ограничениями: «не строй инфраструктуру саму по себе — сразу привяжи к одной конкретной, уже полезной задаче» — генерация объяснения по структуре Recommendation → Why now → Evidence → Expected benefit → Uncertainty для уже сохранённой (Task 8.3) `Recommendation`. **Уточнение цитаты**: Olga сослалась на «§50 DECISION_EXPLANATION», подразумевая контекст `29_AI_LAYER.md` (Phase 9 задана этим документом). При проверке — §50 в `29_AI_LAYER.md` это PROVIDER FAILURE, другой раздел. Точная структура (буквально «Recommendation ↓ Why now ↓ Evidence ↓ Expected benefit ↓ Uncertainty», включая пример) нашлась в `21_DECISION_LOGIC.md` §50 DECISION EXPLANATION — тот же номер раздела, что и предполагала Olga, но в другом документе; вероятно, перенос номера из соседнего обсуждения Phase 9 vs Phase 8. Содержательно её описание точное, поправлен только документ. Обязательные ограничения (`29_AI_LAYER.md`, все процитированы Olga и проверены дословно): §67 AI DOES NOT CONTROL DATABASE, §68 AI DOES NOT CONTROL DOMAIN STATE (baseline/pattern status/recommendation status/user settings), §73 КРИТИЧЕСКОЕ ПРАВИЛО (не строить инфраструктуру без реальной ценности), §74 КРИТИЧЕСКОЕ ПРАВИЛО №2 (не скрывать неопределённость, confidence должен отражать слабый evidence), §75 (провайдер заменяем), §76 КРИТИЧЕСКОЕ ПРАВИЛО №4 (воспроизводимость: модель/версия/prompt/context/evidence/timestamp).

**Решение.**
1. **`AIService`/`AIProvider`/`providers/anthropic.ts` (Task 0.2) не изменены.** Контракт уже поддерживал всё нужное (`task: 'explanation'`, `promptVersion`, `AIRunStatus`) — первая реальная задача AI Layer подтвердила, что MVP-скелет Task 0.2 был спроектирован верно, менять инфраструктуру ради инфраструктуры не потребовалось (§73).
2. **Структурированный output — JSON-через-промпт + ручная валидация**, не SDK-специфичный structured-output/tool-use режим Anthropic. `AIProvider.generate` остаётся текстовым и provider-agnostic (§7 ЗАМЕНА ПРОВАЙДЕРА/§75) — JSON-инструкция в системном промпте работает одинаково для любого текстового провайдера, tool-use API отличается между SDK. `decisionExplanationValidation.ts` проверяет схему (§11 STRUCTURED OUTPUT/§26 AI OUTPUT VALIDATION: 4 обязательных строковых поля, непустые) уже на нашей стороне, до персистентности.
3. **Качественный, не числовой confidence в промпте.** `Recommendation.confidence` в БД — числовое приближение (`CONFIDENCE_SCORE`, D-0022), не измеренная вероятность. Передавать модели голое число 0.5/0.8 создало бы риск псевдо-статистических формулировок («50% вероятность успеха»), которых не существует — прямое нарушение §35 EXPLANATION MUST NOT INVENT. Вместо этого промпт восстанавливает качественную метку (`low`/`medium`/`high`) из уже сохранённого `context.ranking` (Task 8.3, буквально то, что видел `CandidateResult.confidence` в Task 8.1) и явно требует не утверждать больше уверенности, чем она поддерживает (§74).
4. **`AiRun` — новая append-only таблица**, не поле на `Recommendation`. AI не пишет в `Recommendation`/`RecommendationReason`/`Goal`/`Pattern` — только читает их (§67/§68); пишет исключительно в собственную лог-таблицу. Создаётся при ЛЮБОМ исходе (`completed`/`failed`/`timeout`/`provider_unavailable`/`validation_failed`), не только при успехе — §76 требует воспроизводимость решения, включая то, ПОЧЕМУ объяснение не удалось. `status` — Prisma enum `AiRunStatus` (не `String`), т.к. это закрытый набор, заданный собственным контрактом `AIProvider` (`src/ai/AIProvider.ts`), а не открытая платформенная категория вроде `goalType`/`contentType`.
5. **DI-параметр вместо мока `AIService`.** `generateDecisionExplanation(recommendationId, userId, generate = AIService.generate)` — `generate` внедряется явно, не через мокинг модуля. Реальный `AIService` недетерминирован и стоит денег/API quota — интеграционные тесты (кроме одного live-теста) подставляют фиктивную функцию напрямую, без обращения к настоящему Anthropic API. Отдельный `decision-explanation-live.smoke.test.ts` — `describe.skipIf(!process.env.ANTHROPIC_API_KEY)`, тот же принцип, что Instagram (Task 3.2) — реальный end-to-end прогон, не входит в обычный `npm test`, требует явного ключа.

**Обоснование:**
- Один узкий шаг, привязанный к реальной ценности (§73) — не создана общая инфраструктура промптов/AI-раннеров сверх того, что нужно ровно для explanation одной уже существующей `Recommendation`; расширение на другие AI-задачи (content analysis, pattern interpretation) — отдельные будущие шаги, не предвосхищённые здесь.
- Честная неопределённость (§74/§35, прямое требование Olga «честно показывать неопределённость... не выдумывать уверенность») достигается на двух уровнях: промпт получает реальный, не придуманный confidence и явный запрет overclaim; `parseExplanation` не пытается верифицировать содержание текста (это ответственность промпта, не автоматической валидации) — честно разделены роли: schema-валидация против семантической честности.

**Последствия.** Явный, полный `AI_CONTEXT` builder (§19 CONTEXT_BUILDER — отдельный слой, формирующий контекст) не выделен отдельным модулем — сборка контекста сейчас часть `buildExplanationPrompt`, не отдельная переиспользуемая абстракция; если появится вторая AI-задача (например content analysis, §31), стоит пересмотреть. Prompt Registry (§21 PROMPT LAYER — «prompts должны быть отделены от бизнес-логики… Prompt Registry → выбирает нужный prompt») не реализован как отдельная сущность — один промпт на одну задачу, `DECISION_EXPLANATION_PROMPT_VERSION` живёт прямо в `decisionExplanationPrompt.ts`; естественный кандидат на выделение, когда появится вторая версия промпта или вторая AI-задача. `RECOMMENDATION_CANDIDATES`/§27 RANKING_ENGINE-подобный список альтернатив не включён в объяснение отдельно — evidence ограничен тем, что уже сохранено в `RecommendationReason`/`context.ranking`.

## D-0029 — Дополнение к D-0019/D-0027: FRESHNESS_WEIGHT (decay-переоценка baseline) сознательно отложен, не забыт — условия возврата

**Дата:** 15 августа 2026
**Статус:** Принято (YELLOW — техническая неоднозначность с безопасным решением, `CLAUDE.md` §9). Чисто документационная запись — реализация не начиналась и не запланирована этим решением.

**Контекст.** D-0019 (Task 6.2) уже сознательно оставил `computeBaseline` невзвешенным средним по всей истории (`scope: global`, без decay). D-0027 (Task 8.4) реализовал freshness/repetition как качественные сигналы CANDIDATE_SCORER, но явно НЕ тронул сам расчёт `computeBaseline` — decay-переоценка была названа отдельной, более крупной задачей, затрагивающей ANALYSIS layer. Olga просит явно зафиксировать причину отсрочки и условия, при которых к задаче стоит вернуться — не просто «потом», а конкретные, проверяемые триггеры.

**Уточнение цитаты при формулировке.** Olga сослалась на `26_DATA_PIPELINE.md` §36–38. При проверке: §36 в этом документе — SKELETON_UPDATE, §37 — CANDIDATE_GENERATION, §38 — CANDIDATE_DIVERSITY — все три раздела не про freshness weighting вообще, к теме не относятся. Сам термин FRESHNESS_WEIGHT нашёлся только в `21_DECISION_LOGIC.md` §12 (уже процитирован в D-0027 и D-0019 как источник буквальных порогов 0–3/3–6/6+ месяцев) — та же ссылка, что уже использовалась, не новая. Ближайший по смыслу раздел именно в `26_DATA_PIPELINE.md` — §27 DATA_DECAY («вес старых данных должен уменьшаться постепенно… старый результат не должен внезапно становиться "не существует", он становится менее актуальным доказательством») — общий принцип для всего pipeline, не специфичный для baseline-калибровки, но релевантный контекст. Похоже на перенос номера из другого документа при формулировке — содержательный вывод Olga (это FRESHNESS_WEIGHT, часть уже известного пробела D-0019/D-0027) остаётся верным, поправлен только номер/документ.

**Решение.** Реализация FRESHNESS_WEIGHT (decay-переоценка `computeBaseline`, `21_DECISION_LOGIC.md` §12, в духе `26_DATA_PIPELINE.md` §27 DATA_DECAY) сознательно откладывается — не потому что неважна, а потому что калибровка формулы затухания при минимальном объёме реальных данных означала бы гадать вслепую: ровно та ложная точность (§40 NO FALSE PRECISION), которой весь проект последовательно избегает (D-0019, D-0024, D-0025, D-0026, D-0027 — все явно отказались придумывать веса/пороги без реальной опоры).

Условия возврата к задаче (**любое** из трёх):
1. Накопится достаточно реальной истории публикаций за несколько месяцев, чтобы формулу можно было откалибровать на настоящих, а не воображаемых данных.
2. Проект вплотную подойдёт к Phase 10 (запуск для реальных пользователей).
3. Обнаружится конкретный случай, где плоское (невзвешенное) среднее по всей истории `computeBaseline` даёт заметно неверный вывод.

**Обоснование.** Прямое продолжение принципа, установленного с D-0019: baseline — простое среднее, пока нет причины усложнять; decay-формула, откалиброванная «на глаз» при 5–20 публикациях у тестового пользователя, была бы придуманным числом, которое выглядело бы наукообразно, но не опиралось бы ни на что реальное — хуже, чем честное признание «пока не взвешиваем».

**Последствия.** Задача не создаётся в `TASKS.md` заранее (тот же принцип, что «Следующая рекомендованная задача» — не расписывается, пока не наступит очередь); эта запись в `DECISIONS.md` — единственное место, где решение и условия возврата зафиксированы, до того момента `computeBaseline`/`personalBaseline.ts` не трогаются ради этой темы. Если условие 3 наступит раньше условий 1/2 (найден конкретный случай неверного вывода) — это, скорее всего, будет обнаружено через `DataQuality`/`Pattern`/реальное использование, не через отдельный аудит.
