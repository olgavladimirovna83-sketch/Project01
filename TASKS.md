## Phase 0 — Project Foundation

### Task 0.1 — Инициализация репозитория
**Цель:** создать git-репозиторий (local + remote GitHub), базовую структуру папок (`/docs`, `/src`, `/tests`).
**Спецификация:** `42_IMPLEMENTATION_ROADMAP.md`, Phase 0.
**Готово, когда:** репозиторий создан, README есть, первый коммит запушен в remote.

### Task 0.2 — Настройка технического стека
**Цель:** инициализировать Next.js + TypeScript проект, подключить Prisma, создать структуру папок согласно слоям (Data/Analysis/Knowledge/Decision/AI/UI). Сразу заложить обязательные абстракции из `CLAUDE.md` §4.1: `AIProvider`, `ObjectStorageService`, data-access слой для Postgres, заготовку под `ExternalIntegration`-адаптеры — даже пустыми, чтобы domain-код с первого дня не мог напрямую импортировать Anthropic SDK или провайдерские клиенты.
**Спецификация:** `CLAUDE.md` §3–4.1, `24_TECHNICAL_ARCHITECTURE.md`, `29_AI_LAYER.md`.
**Готово, когда:** `npm run dev` поднимает пустое приложение локально без ошибок, а структура папок физически отражает границы слоёв.

### Task 0.3 — Окружения и конфигурация
**Цель:** development и staging окружения, структура `.env`, secrets management вне git.
**Спецификация:** `30_SECURITY_PRIVACY.md` §62–63; `46_PRODUCTION_OPERATIONS_AND_RELIABILITY.md` §3–4.
**Готово, когда:** dev и staging изолированы по credentials и конфигурации.
**Статус:** repo-часть готова — `ENVIRONMENTS.md` (стратегия трёх окружений, правило изоляции), расширенный `.env.example`, `.gitignore` подтверждён. Инфраструктурная часть (реальные Vercel/Neon/Upstash/R2 ресурсы для staging/production) не создана — требует доступа Olga к внешним дашбордам, Claude Code не имеет соответствующих аккаунтов/API-ключей.

### Task 0.4 — Базовый CI
**Цель:** GitHub Actions pipeline (lint, type-check, tests, build) на каждый PR.
**Спецификация:** `46_PRODUCTION_OPERATIONS_AND_RELIABILITY.md` §7; `35_TESTING_QUALITY_CONTROL.md` §53.
**Готово, когда:** PR не мержится при падении критичных проверок.
**Важно:** при `npm install` в CI (как и локально при верификации Task 0.2) `@prisma/client`-postinstall не всегда генерирует клиент автоматически (наблюдалось из-за `allow-scripts`-политики npm). CI pipeline должен явно включать шаг `npx prisma generate` перед `type-check`/`build` — иначе сборка будет падать на отсутствии сгенерированного Prisma Client.
**Статус:** pipeline готов (`.github/workflows/ci.yml`: lint → type-check → build; шаги для тестов добавляются в Task 0.5), все шаги проверены локально. **Не сделано:** required status checks / branch protection для `main` в GitHub Settings — в этой среде нет `gh` CLI, и это repo-настройка вне scope автоматического выполнения агентом. Без этого шага PR технически может быть смёрджен при падении CI — буквальный Definition of Done («PR не мержится при падении критичных проверок») требует ручного действия Olga: Settings → Branches → Branch protection rule для `main` → Require status checks to pass → выбрать check `Lint, type-check, build`.

### Task 0.5 — Инициализация тестового фреймворка
**Цель:** настроить Vitest (unit/integration) и Playwright (E2E), по одному smoke-тесту на каждый.
**Спецификация:** `35_TESTING_QUALITY_CONTROL.md`.
**Готово, когда:** `npm test` и E2E smoke проходят локально и в CI.
**Статус:** Завершена. `vitest.config.ts` + `tests/unit/ai-service.smoke.test.ts`, `playwright.config.ts` + `tests/e2e/home.spec.ts`. `npm test` и `npm run test:e2e` проверены локально — оба проходят (1 passed каждый). CI (`.github/workflows/ci.yml`) расширен шагами `npm test` и `npx playwright install --with-deps chromium` + `npm run test:e2e` — фактический прогон в CI не подтверждён (нет открытого PR/push, требующего срабатывания workflow; будет подтверждено первым же PR/push после этого коммита).

### Task 0.6 — Проверка завершения Phase 0

### Task 2.2 — Registration / Login / Logout (UI + API) + верифицированный HTTP session cycle
**Цель:** поверх технической основы Task 2.1 (`src/auth/`) реализовать практический вход в приложение: страницы/формы registration и login, действие logout, API-роуты для них, и один минимальный protected route (например `/api/me`), чтобы подтвердить критерий Phase 2 completion (`42_IMPLEMENTATION_ROADMAP.md` §11: «создать account → войти → получить доступ только к своим данным»). **Обязательно закрыть пробел, явно оставленный в Task 2.1**: e2e-тест (Playwright) должен пройти полный HTTP-цикл через реальный браузер — регистрация → login → issuance cookie-based JWT-сессии через реальный `/api/auth/*` endpoint → доступ к protected route → logout → сессия инвалидирована, protected route снова недоступен. Не просто unit/integration-уровень `authenticateWithCredentials` (это уже сделано в Task 2.1) — именно реальный HTTP round-trip.
**Обязательные требования по ходу реализации** (не «потом»): input validation на registration/login endpoints (формат email, минимальная длина/сложность пароля — `CLAUDE.md` §6, §7 `30_SECURITY_PRIVACY.md`); понятная обработка попытки регистрации на уже занятый email (без утечки существования/несуществования аккаунта сверх необходимого); logout корректно инвалидирует сессию (`30_SECURITY_PRIVACY.md` §8); базовая user isolation — protected route у двух разных зарегистрированных пользователей возвращает каждому только его собственные данные, e2e-тестом подтверждается на двух созданных аккаунтах, не на одном (`CLAUDE.md` §6, §7; `30_SECURITY_PRIVACY.md` §5, §10).
**Явно не входит в эту задачу** (следующие отдельные задачи, не расписываются заранее): account recovery / password reset — обычно требует email-сервиса, потенциальная новая RED-точка по той же логике, что и в D-0009; authorization/roles/admin permissions (`42_IMPLEMENTATION_ROADMAP.md` §10 — team accounts, будущее); rate limiting на auth endpoints — `CLAUDE.md` §6 требует его для публичных endpoints как часть MVP, не «потом», но stack-решение для этого — BullMQ/Redis (D-0001), а реальный Redis/Upstash сознательно отложен (`DECISIONS.md` D-0007); это осознанный, явно зафиксированный здесь gap, не тихий пропуск — закрывается либо при появлении Redis-инфраструктуры, либо отдельным YELLOW-решением до этого момента.
**Спецификация:** `42_IMPLEMENTATION_ROADMAP.md` §9, §11; `CLAUDE.md` §3.2/§4.1/§6/§7; `30_SECURITY_PRIVACY.md` §5–8.
**Готово, когда:** e2e-тест (Playwright) проходит полный HTTP-цикл, описанный выше, для минимум двух независимых пользователей и подтверждает user isolation; registration/login отклоняют невалидный ввод (пустой/некорректный email, слишком короткий пароль) с понятным ответом, не 500-ошибкой; повторная регистрация на тот же email не создаёт дубликат и не роняет сервер; `npm run test:e2e`, `npx tsc --noEmit`, `npm run lint`, `npm run build` проходят локально и в CI.
**Статус:** Завершено. `src/auth/register.ts` — `registerUser(email, password)`: валидация email/пароля (мин. 8 символов), проверка занятого email, хеширование (`bcryptjs`, переиспользован из Task 2.1), создание через `userRepository`. `src/app/api/register/route.ts` — 201/400/409 по типу ошибки. `src/app/api/me/route.ts` — единственный protected route: 401 без сессии, иначе перечитывает пользователя из БД по `session.user.id` (не доверяет claims напрямую, resource ownership). `src/app/login/page.tsx`, `src/app/register/page.tsx` — клиентские формы на `signIn('credentials', ...)` / `fetch('/api/register')`. `src/app/_components/LogoutButton.tsx` — `signOut({ callbackUrl: '/' })`. `src/app/page.tsx` — теперь async server component, показывает logged-in/logged-out состояние через `auth()`. `src/auth/config.ts` дополнен `pages: { signIn: '/login' }`. **Пробел из Task 2.1 закрыт**: `tests/e2e/auth-flow.spec.ts` (5 тестов, реальный браузер через Playwright) — register issues session → `/api/me` 200 → logout → `/api/me` 401; login с верным паролем работает; login с неверным паролем не создаёт сессию (`/api/me` остаётся 401); два независимо залогиненных пользователя (два `browser.newContext()`) видят через `/api/me` только свои собственные данные (user isolation). Один race condition найден и исправлен в самом e2e-тесте по ходу работы (logout — асинхронная навигация, тест не дожидался её завершения перед переходом на `/login`, из-за чего старая cookie иногда переживала переход) — не баг приложения, задокументировано как урок в TASKS.md. `tests/integration/auth-registration.smoke.test.ts` — `registerUser` против живой БД: хеширование пароля (не plaintext в БД), отклонение дубля email/невалидного email/короткого пароля. Rate limiting на auth endpoints сознательно не реализован в этой задаче (блокер — Redis не поднят, см. `DECISIONS.md` D-0007) — не тихий пропуск, см. выше. Account recovery/authorization/roles — не в этой задаче, следующие шаги Phase 2. `npx tsc --noEmit`, `npm run lint`, `npm run build`, `npm test` (4 файла/7 тестов), `npm run test:e2e` (5/5) — все прошли; dev-БД `olga` проверена — 0 тестовых пользователей после прогонов.

### Task 2.3 — Authorization foundation: переиспользуемый ownership-check + первый защищённый ресурс за пределами User
**Цель:** реализовать `30_SECURITY_PRIVACY.md` §9–10 (authorization + resource ownership) как переиспользуемый паттерн, а не одноразовый код внутри `/api/me`. Вынести получение user id из сессии в общий хелпер в `src/auth/`, использовать его в `/api/me` (рефакторинг существующего кода) и в новом ownership-protected endpoint для сущности, отличной от `User`. Для этого шага выбрана `Goal` — простейшая существующая сущность с полем `userId` (`prisma/schema.prisma`, `src/data/repositories/goalRepository.ts`) — чтобы доказать, что паттерн обобщается на произвольный ресурс, не жёстко прибит к одному route.
**Явно не входит в эту задачу** (сознательно откладывается, не расписывается заранее): role model (owner/admin/editor/viewer) — `30_SECURITY_PRIVACY.md` §11 прямо говорит «для MVP достаточно user-level authorization», team accounts не в scope продукта на этом этапе; service permissions (машина-к-машине, авторизация BullMQ-воркеров) — фоновых задач ещё нет, нечего авторизовывать; password reset / account recovery — сознательно отложено ещё в D-0009, к этому вернёмся отдельно, чтобы не упереться в RED-точку с email-сервисом раньше времени; полный CRUD для `Goal` (list/delete) — только то, что нужно для проверки ownership-механизма (create + get by id), по тому же принципу минимализма repository-слоя, что и в Task 1.2/2.1 (`не более того, что реально понадобится ближайшим фазам`).
**Спецификация:** `42_IMPLEMENTATION_ROADMAP.md` §10 (из перечисленных там user permissions/service permissions/administrative roles — в этой задаче только user permissions); `30_SECURITY_PRIVACY.md` §9–11 (authorization, resource ownership — пример из документа буквально «content_id сам по себе не является разрешением на получение content»; role model — явно вне MVP-scope).
**Готово, когда:** общий хелпер (например `requireSessionUserId()`) в `src/auth/` используется и в `/api/me`, и в новом endpoint; `POST /api/goals` создаёт `Goal` с `userId` из сессии — тело запроса не может указать чужой `userId` (сам этот факт — часть authorization control, не отдельная проверка); `GET /api/goals/:id` возвращает goal только если `goal.userId === session.user.id`; если goal принадлежит другому пользователю ИЛИ не существует — единообразный `404` (не `403`), чтобы не раскрывать факт существования чужого ресурса (`30_SECURITY_PRIVACY.md` §10); тест подтверждает: пользователь A создаёт goal → A может его прочитать → пользователь B (другая сессия) получает `404` на тот же `goal_id`, не доступ к данным и не намёк на существование; `npx tsc --noEmit`, `npm run lint`, `npm run build`, `npm test`/`npm run test:e2e` проходят локально и в CI.
**Статус:** Завершено. `src/auth/session.ts` — `requireSessionUserId()`, единая точка получения user id из сессии; `src/app/api/me/route.ts` отрефакторен на её использование (без изменения поведения). `src/app/api/goals/route.ts` (`POST` — создаёт `Goal` с `userId` строго из сессии, тело запроса не может указать чужой `userId`) и `src/app/api/goals/[id]/route.ts` (`GET` — `404` единообразно и для несуществующего, и для чужого goal, чтобы не раскрывать факт существования). `tests/e2e/helpers/auth.ts` — общий `registerAndLogin`/`uniqueEmail`-хелпер, вынесен из `auth-flow.spec.ts` (Task 2.2) для переиспользования, без дублирования между спеками. `tests/e2e/goal-authorization.spec.ts` (3 теста, реальный браузер) подтверждает: неаутентифицированный запрос к `/api/goals` — `401`; владелец создаёт и читает свой goal; второй залогиненный пользователь получает `404` и на чужой goal, и на несуществующий id — коды ответа неотличимы (доказательство, что ownership-check не палит существование). ## Phase 3 — предварительное условие (зафиксировано по итогам review, D-0003)

### Task 3.0 — Техническая проверка Instagram/Meta Graph API
**Цель:** проверить актуальные требования Meta/Instagram Graph API перед реализацией OAuth-интеграции: необходимые permissions, business/creator account requirements, token lifecycle (issuance, refresh, expiry, revocation), доступность нужных метрик через API, rate limits, webhook-поддержку.
**Спецификация:** `CLAUDE.md` §4.1 (Instagram/Auth boundary), `08_METRICS_FRAMEWORK.md`, `26_DATA_PIPELINE.md`.
**Готово, когда:** есть письменное резюме — какие permissions запрашивать, какие данные реально доступны, как устроен token lifecycle. Только после этого начинается реализация Integration Service.
**Статус:** Завершено (research-only). Письменное резюме — [`INSTAGRAM_API_REVIEW.md`](INSTAGRAM_API_REVIEW.md) (корень репозитория). Ключевые находки: (1) современный путь подключения — **Business Login for Instagram**, Facebook Page не требуется (в отличие от старого Facebook Login flow); (2) вероятно достаточно одного scope — `instagram_business_basic`, остальные (content_publish/manage_messages/manage_comments) не нужны для MVP-цели (аналитика, не постинг/messaging); (3) token lifecycle: short-lived (~1ч) → long-lived (60д) → refresh (не раньше 24ч, не позже истечения, снова 60д) — официальная документация не описывает явно сценарий полного истечения без refresh, спроектировано с расчётом на graceful reconnect-flow; (4) метрика `impressions` **deprecated с апреля 2025**, заменена на `views` — это меняет маппинг метрик из `08_METRICS_FRAMEWORK.md` §2 на этапе реализации Data layer, не сейчас; (5) история метрик у Instagram хранится **90 дней** — подтверждает, не расширяет, цель «~3 месяца» из `08_METRICS_FRAMEWORK.md` §12; (6) rate limiting — per-account (4800 × охват за 24ч), не глобальный лимит на приложение; (7) webhooks не покрывают performance-метрики (только comments/mentions/story-insights) — подтверждает, что polling/incremental sync (уже заложенный в `26_DATA_PIPELINE.md`) остаётся правильной архитектурой; (8) **организационное следствие**: реальный запуск для сторонних пользователей потребует Meta App Review + Business Verification (Advanced Access), не только Standard Access, доступный для разработки — стоит учитывать в планировании таймлайна MVP launch, не только в архитектуре. Явные пробелы в исследовании (endpoint revocation, точная scope-to-endpoint матрица) зафиксированы честно в файле, не выданы за проверенный факт. Meta developer-аккаунт/приложение **не создавались** — RED, ждёт Olga. Не блокирует Phase 3 планирование дальше.
**Уточнение (12 августа 2026):** Olga лично прошла реальную авторизацию Instagram (существующий flow, не создание нового Meta developer-аккаунта/приложения) и подтвердила фактический набор permissions — это исправило вывод исходной версии резюме. Разрешены: `instagram_business_basic` (обязательный) + **отдельное insights-разрешение** (на консент-экране показано отдельно от `instagram_business_basic`, не частью его, как предполагалось изначально). Осознанно отключены: comments/messages/content-publish. `INSTAGRAM_API_REVIEW.md` §3 обновлён — исправленный вывод для MVP и статус связанного gap в §8 (точное каноническое имя scope для insights в Business Login остаётся открытым вопросом, но сам факт отдельного разрешения подтверждён первичным источником — Olga, выше документации по `CLAUDE.md` §2).
